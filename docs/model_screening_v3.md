# Пункт 2. Сравнение моделей перед новым SFT

Подготовлен отдельный запуск для `Qwen/Qwen3-4B-Instruct-2507` и `microsoft/Phi-4-mini-instruct` на development v3. Одна модель получает 32 вопроса с двумя системными промптами, всего 64 ответа. Два запуска дадут 128 ответов для содержательного сравнения.

[Открыть ноутбук в Google Colab](https://colab.research.google.com/github/maria-igntv/lm-hw/blob/main/notebooks/00_model_screening_v3.ipynb).

## Что проверяем

Сначала проверяем технический путь от текста до ответа. Нужны правильный формат диалога, нужный токен начала ответа, полный список EOS и конечные значения logits. Затем смотрим, может ли модель выполнить короткую инструкцию и расчёт по-русски и по-английски. Первый короткий greedy-запрос повторяется для проверки совпадения токенов.

Основной прогон сравнивает качество на бытовых задачах. `general` просит краткий русский ответ. `household` дополнительно задаёт безопасное поведение, работу с недостающими данными и практическую помощь в обычных случаях. Эти два промпта зафиксированы в протоколе. Такой эксперимент покажет, насколько уже помогает специализированный промпт и какая база подходит для следующего SFT.

Новые ответы и оценки моделей на момент подготовки ещё не получены. Реальный T4 inference smoke выполняется внутри этого ноутбука. Проверка LoRA-обучения относится к следующему пункту 3.

## Первый запуск с Qwen3

1. Откройте Colab по ссылке выше.
2. Выберите **Среда выполнения → Сменить среду выполнения → T4 GPU**. В английском интерфейсе это **Runtime → Change runtime type → T4 GPU**.
3. В первой кодовой ячейке оставьте строку ниже.

   ```python
   MODEL_KEY = "qwen3_4b"
   ```

4. Выполняйте ячейки по порядку. Также можно выбрать **Среда выполнения → Выполнить все**. Загрузка весов требует интернета и может занять несколько минут.
5. В секции технических контролей посмотрите четыре ответа. Для однословного запроса ожидается выполнение инструкции, для расчёта — 1,2 кВт·ч. В конце будут выведены совпадение токенов при повторе, пустые контроли и обнаруженные CJK-символы. Сам численный ответ на контроль проверяем по содержанию.
6. Дождитесь строки **«Сохранено ответов 64»** и экспорта 64 заданий судье. В автосводке должны быть `complete=true`, `expected_n=64`, по 32 ответа для `general` и `household`.
7. Последняя ячейка скачивает архив с именем вида `screening_v3_qwen3_4b_t768_<хеш>.zip`. Если браузер запросит разрешение на загрузку, разрешите его.
8. Дополнительно выберите **Файл → Скачать → Скачать файл IPYNB**. Этот файл сохранит вывод ячеек, сообщения и примеры ответов.

У нормального технического прогона ожидаются `last_logits_finite=true`, `greedy_tokens_equal=true`, `empty_control_ids=[]` и `ru_controls_with_cjk=[]`. Logits — численные значения, из которых модель выбирает следующий токен. NaN или Inf в них указывают на численную проблему. Смысловая правильность русских и английских контролей проверяется по их текстам.

Рабочая копия создаётся в `/content/lm-hw-v3`. Папка результата будет напечатана в секции 1. Хеш в имени учитывает код, входные данные, модель и фактическую среду. Это позволяет отличать запуски с разными условиями.

## Второй запуск с Phi

1. Сохраните ZIP и выполненный IPYNB первого запуска.
2. Завершите текущую сессию через меню среды выполнения и откройте новую с T4. В интерфейсе Colab пункт может называться **Отключиться и удалить среду выполнения** или **Disconnect and delete runtime**.
3. Откройте свежий ноутбук по той же ссылке.
4. В первой кодовой ячейке измените одну строку.

   ```python
   MODEL_KEY = "phi4_mini"
   ```

5. Выполните ячейки по порядку. Дождитесь 64 сохранённых ответов и 64 экспортированных заданий.
6. Скачайте `screening_v3_phi4_mini_t768_<хеш>.zip` и выполненный IPYNB.

На анализ понадобятся **два ZIP и два выполненных IPYNB**. Веса моделей скачиваются из Hugging Face при загрузке. Итоговые архивы содержат результаты и условия эксперимента.

## Как понимать автосводку

- `eos_stops` показывает ответы, завершённые одним из опубликованных EOS-токенов своей модели.
- `length_stops` показывает достижение лимита без завершающего EOS. Такой ответ мог оборваться. Если EOS выпал последним токеном ровно на лимите, он учитывается как завершение по EOS.
- `empty_answers` показывает пустые тексты. Они сохраняются и оцениваются как полученные результаты.
- `answers_with_cjk` отмечает иероглифы для просмотра. Доля кириллицы в каждой записи учитывает все буквенные символы, включая CJK.
- `answers_with_repetition` использует имеющуюся n-gram-проверку проекта.
- `dangerous_with_warning_marker` и `ordinary_with_warning_marker` показывают обнаружение regex-маркера в двух группах вопросов.

Для новой выборки корректный короткий расчёт может занимать одно предложение. Длина и наличие маркера сами по себе содержательного прохождения не дают. Решение определяется критериями [development v3](../data/development_v3/README.md).

## Если выполнение прервалось

В той же живой сессии повторно выполните ячейку основной генерации. Уже сохранённые пары вопрос / промпт будут проверены и пропущены. После каждого нового ответа `answers.jsonl` заменяется атомарно, чтобы прерывание записи сохраняло предыдущую полную версию файла.

При ошибке после создания `OUT_DIR` выполните две последние кодовые ячейки для экспорта и скачивания имеющихся результатов. Неполный результат помечается `complete=false`. Сообщение об ошибке сохраняется в `errors.jsonl`. Если ошибка возникла при установке или импорте до создания папки результата, скачайте выполненный IPYNB с traceback.

Если Colab сообщает, что библиотека уже импортирована в другой версии, перезапустите сеанс Python и снова выполните ячейки. При `CUDA out of memory` сохраните частичный результат и вывод ячеек. Уменьшение лимита в одном запуске создаст другой протокол сравнения. Изменённые условия нужно применять согласованно к обоим кандидатам и учитывать при анализе.

## Как запустить того же судью

Сначала нужно получить оба архива. Затем можно оценить все 128 заданий одной серией тем же Qwen3.8-27B.

1. Объедините строки двух `judge_requests.jsonl`. `request_id` строится из идентификатора прогона и пары вопрос / промпт, имена кандидатов в запросах скрыты.
2. Используйте `system_prompt` и `user_prompt` из каждой строки. Для DAG с общим системным промптом возьмите `judge_system_prompt.md`, содержимое одинаково для двух архивов одной версии.
3. Передайте схему из `judge_response_schema.json`. В `judge_run_config.json` уже сформировано поле `response_format` для API, принимающего JSON Schema.
4. Параметры для этой версии — `temperature=0`, `max_tokens=2048`, один вызов на один ответ. Это 128 заданий, реальный расход зависит от длины ответа судьи.
5. Сохраните `request_id`, весь JSON с оценками и проверками критериев, сырой ответ, ошибки и метаданные модели / запуска. Нужны все поля новой схемы, включая `criteria_checks`, `critical_errors`, `major_errors`, `unsupported_specifics` и `needs_review`.

Новая версия судьи оценивает достаточность ответа для конкретной задачи. Полезность максимального балла допускает краткий расчёт, достаточное уточнение или безопасный аварийный следующий шаг. Абсолютные средние старых прогонов v1 и новых шкал рассматриваются с учётом изменения протокола. После возвращения оценок доля содержательных прохождений будет вычислена по критериям, а спорные случаи разобраны по текстам.

## Какой результат нужен для перехода к пункту 3

Нужны полные ответы обоих кандидатов, технические логи, содержательная оценка и разбор критических ошибок. Основные показатели — доля прохождений, число критических ошибок, полезность обычных ответов и выдуманные детали. Отдельно сравнивается эффект `household` относительно `general` внутри каждой модели.

После этого выбираем модель и промпт для нового SFT и проверяем загрузку, обучение и сохранение LoRA на реальной T4. Победитель нового цикла по текущим артефактам ещё не определён.

## Проверки при подготовке

Проверены структура IPYNB, синтаксис кодовых ячеек, целостность development-набора, обработка EOS на лимите, учёт пустых ответов, CJK, независимость пар вопрос / промпт и экспорт судейских заданий. На реальных файлах токенизаторов двух закреплённых ревизий проверены шаблоны, начало ответа и оба EOS. API функции генерации проверен на уменьшенных моделях со случайными весами на CPU. Эти проверки не измеряют качество полных моделей. GPU-загрузка полных моделей, времена и содержательные метрики будут получены в Colab.
