# Пункт 6. Содержательный SFT-пилот

Подготовлен [04_sft_v3_pilot.ipynb](../notebooks/04_sft_v3_pilot.ipynb).
Он обучает свежую LoRA на 80 train-примерах и сравнивает исходную модель
с обученной на 32 development-вопросах. Реальный запуск этого пилота
на T4 и содержательная оценка его ответов ещё предстоят.

## Что нужно сделать сейчас

1. Откройте [ноутбук в Google Colab](https://colab.research.google.com/github/maria-igntv/lm-hw/blob/main/notebooks/04_sft_v3_pilot.ipynb).
2. Создайте новую сессию: **Среда выполнения → Сменить среду выполнения → T4 GPU**.
   Потребуется доступ к интернету для загрузки библиотек и базовой модели.
3. Выполняйте ячейки сверху вниз. Выбирать модель и загружать файлы вручную
   не требуется. Ноутбук сам скачает зафиксированный корпус и исходную модель.
   Обучение начинается со свежей LoRA; веса предыдущих smoke и tiny здесь не используются.
4. Если после установки библиотек потребуется перезапуск Python, перезапустите
   его и выполните ячейки заново с первой. После загрузки модели продолжайте
   по порядку.
5. Дождитесь 32 baseline-ответов, 20 шагов обучения и ещё 32 SFT-ответов.
   На генерации выводится счётчик `1 / 64` … `64 / 64`.
   Измерения loss на шагах 0, 10 и 20 также занимают время.
6. После проверки загрузки и экспорта должен появиться **`PILOT PIPELINE PASS`**.
7. Выполните последнюю ячейку. Браузер скачает
   `sft_v3_pilot_<run_id>.zip`, обычно в папку «Загрузки» на компьютере.
   Если скачивание заблокировано, разрешите его и повторите последнюю ячейку.
8. Сохраните выполненный ноутбук: **Файл → Скачать → Скачать файл IPYNB**.
   Для разбора нужны ZIP и IPYNB из одной сессии; Run ID печатается в выводе.

Папка внутри Colab:
`/content/lm-hw-v3/results/sft_v3_pilot/<run_id>/`.
Само обучение относительно короткое; основное время может занять загрузка
модели и генерация 64 ответов. Полное время этого пилота на T4 пока не измерено.

## Что именно обучается

| Параметр | Значение |
| --- | --- |
| База | Qwen/Qwen3-4B-Instruct-2507 |
| Ревизия | cdbee75f17c01a7cc42f958dc650907174af0554 |
| Промпт | household из selection.json |
| Загрузка | NF4, double quantization, FP16, eager attention |
| LoRA | r=16, alpha=32, dropout=0, семь attention/MLP-проекций |
| Данные | 80 train, 16 validation, восемь категорий в обеих частях |
| Режим | одна эпоха, 20 optimizer steps |
| Batch / накопление | 1 / 4 |
| Оптимизатор | AdamW, постоянный LR=5e-5, weight decay=0, clipping=1 |
| Обучающий контекст | 768 токенов, right padding, усечение запрещено |
| Loss | только ответ ассистента и завершающий EOS |
| Измерения train/validation | шаги 0, 10, 20 |
| Итоговый checkpoint | шаг 20, зафиксирован до запуска |

Все 80 train-примеров используются по одному разу, что проверяется
по журналу микробатчей. Восемь примеров предыдущего tiny-эксперимента
входят в эти 80, но обучение стартует заново с исходной базы.
Validation содержит другие группы сценариев и не участвует в градиентах.
Падение validation loss показывает лучшее соответствие отдельным эталонам
в режиме teacher forcing. Для вывода о качестве нужны свободные ответы.

Настройки закреплены в [pilot_config.json](../data/sft_v3/pilot_config.json).
Повторно используется оптимизаторный цикл, проверенный в tiny-эксперименте;
в этом запуске он получает все 80 примеров и выполняет одну эпоху.
Точная версия корпуса и development закреплена хешами manifest.json.
Авторская проверка корпуса завершена; дополнительная независимая
проверка 96 эталонов судьями пока не получена.

## Как обеспечено сравнение до и после

В одной сессии сначала сохраняются 32 ответа исходной модели, затем
обучается LoRA и сохраняются 32 ответа SFT. Подготовка модели к k-bit
может немного менять вычисления: обе серии используют одну и ту же
уже подготовленную базу. До baseline проверяется нулевой вклад свежей LoRA.
После обучения logits отключённой базы сравниваются с исходным состоянием
на трёх фиксированных контрольных вопросах.

Генерация получает только системный промпт и вопрос. Эталон,
категория, признаки опасности и рубрика модели не передаются.
Условия совпадают с development-скринингом: sampling, temperature=0.7,
top_p=0.8, top_k=20, min_p=0, repetition_penalty=1, максимум 768 новых токенов.
Для вопроса с порядковым номером i используется seed=20261116+i
в обеих сериях. Исходные ответы генерируются заново в этой сессии.

Один seed на вопрос ограничивает оценку случайной вариативности.
При небольшом преимуществе потребуются повторы до принятия решения.
Development уже участвовал в выборе модели и промпта; окончательное
подтверждение потребует отдельного теста после выбора конфигурации.
Зафиксированная неоднозначность dev3_02 сохранена в review_notes.json;
итог нужно также пересчитать без этого вопроса.

## Как оценить ответы судьёй

1. Распакуйте основной ZIP на компьютере. Откройте папку запуска,
   затем `judge/`. Для разметки передайте **for_judge.zip**.
2. Используйте прежнего судью **Qwen3.8-27B**, temperature=0,
   max_tokens=2048 и схему из `judge_response_schema.json`.
   При возможности тот же пакет можно независимо оценить gemma-4-31B-it.
3. Для каждой строки `judge_requests.jsonl` передайте `system_prompt`
   как system-сообщение и `user_prompt` как user-сообщение.
   Поле user_prompt — готовая JSON-строка с вопросом, точным ответом,
   критериями и основаниями. Добавлять инструкцию в текст ответа не требуется.
   `judge_run_config.json` содержит параметры и response_format.
4. Сохраните исходный request_id, все поля JSON-ответа по схеме,
   сырой ответ судьи, ошибки и метаданные запуска. Ожидаются **64 из 64**
   валидных оценок отдельно от каждого судьи. Ошибки следует повторить
   с прежними параметрами и тем же request_id; содержательные баллы не меняют вручную.
5. Пришлите оценки и метаданные вместе с основным результатом пилота.
   Таблица judge_mapping.json позволит восстановить пары baseline/SFT.

Запросы перемешаны, request_id непрозрачны, название модели и фаза скрыты.
Таблица соответствия в for_judge.zip не входит. Ноутбук сам не обращается
к внешнему API судьи.

## Как решим, что делать дальше

Сравним долю ответов, удовлетворяющих всем обязательным критериям без
существенных ошибок, число критических рекомендаций, helpfulness,
необоснованную конкретику и отказы. Разберём пары, где ошибка исправилась
или появилась. Отдельно посмотрим опасные и обычные вопросы,
обрезания, пропуски оценок и чувствительность к dev3_02.
Regex показывает наличие маркера предупреждения; безопасность
подтверждается содержанием действий.

Ориентир для расширения корпуса — улучшение содержательной полезности
и выполнения критериев без роста критических ошибок. Новую критическую
рекомендацию нужно разобрать, даже если средний балл вырос.
При близких результатах решение остаётся открытым до повторов.
Если пилот ухудшит ответы, сначала разберём конкретные ошибки,
эталоны и изменение поведения; следующая конфигурация будет отдельным экспериментом.

## Что проверено при подготовке

Пройдены 35 локальных тестов, в том числе сохранение незавершённой
генерации, одинаковые seed в парах и передача точного текста судье.
С настоящим токенизатором пересчитаны маски всех 96 примеров
и проверены 32 входа генерации. Формат ноутбука валиден,
все ячейки Python компилируются.

На маленькой случайной Qwen3 на CPU тот же цикл выполнил 20 шагов,
использовав 80 примеров ровно по одному разу; базовые веса сохранились,
а logits и greedy-токены после загрузки адаптера совпали точно.
Экспорт проверен на 64 искусственных ответах с настоящими критериями:
состав пакета, соответствие пар, точность текста и итоговая ячейка отчёта.
Эти проверки подтверждают работу кода. Работа полной 4B-модели в NF4
на T4 в этом пилоте подтверждается выполнением ноутбука пользователем.

## Если возникнет ошибка

Генерация сохраняет каждый ответ. Пока текущая GPU-сессия жива,
повтор её ячейки пропускает уже сохранённые вопросы.
После начала обучения повтор исходной серии заблокирован.
После частичного сбоя обучения сохраните ZIP и IPYNB;
для полного повторения нужна новая сессия с исходной базой и свежей LoRA.
Автоматического восстановления оптимизатора после потери сессии нет.

Последнюю ячейку скачивания можно выполнить после любой ошибки,
если OUT_DIR уже создан. Если ошибка возникла раньше,
сохраните выполненный IPYNB с выводом. `PILOT PIPELINE PASS`
не заменяет содержательную оценку: до получения оценок статус качества —
`awaiting_judge_scores_and_content_review`.
