# Внешний запуск 32 новых судейских оценок

Локальная среда не содержит авторизованного клиента или ключа для сервиса,
в котором выполнялись прежние запуски GigaHF. Новые запросы моделям здесь не
отправлялись. Нужно выполнить два внешних пакетных запуска по 16 заданий.
Нельзя заменять модели собственным чтением ответов или другой LLM.

## Зафиксированный вход

Использовать только `judge/adapter_strength_v1/for_judge.zip`:

- SHA-256: `c4815f8258471e4d1362522626ca175b4434994bda276b9338d1117c44a4159a`;
- 16 строк `judge_requests.jsonl`, по восемь ответов для каждого из двух скрытых масштабов;
- системный промпт SHA-256: `569c99ed711c1937c4dd06a196f295e458e83b7adf71c32e4185c7758fd93ff0`;
- схема SHA-256: `4525f37cd34bafd3bdd68e6494f0f1caba759e3c4bf31b51a6855d97c239c662`.

Для каждой строки передать `system_prompt` как system-сообщение,
`user_prompt` как user-сообщение и сохранить `request_id` без изменений.
Текст запроса, ответ ассистента, критерии и источники не редактировать.
`judge_mapping.json`, прежние баллы, масштабы и авторский разбор судьям не передавать.

## Модели и параметры

Нужны отдельные запуски фактически доступных в каталоге моделей:

1. `Qwen3.8-27B`; в прежнем сопоставимом запуске catalog provider=`Qwen`,
   engine=`vllm`, backend=`coordinator`, alias=`Qwen3.8-27B-FP8`.
2. `gemma-4-31B-it`; в прежнем запуске catalog provider=`google`,
   engine=`vllm`, backend=`coordinator`.

Это сведения о прежнем каталоге, а не разрешение молча подставить их вместо
фактических метаданных нового запуска. Если имя, модель или протокол изменились,
записать фактическое значение; анализатор отдельно отметит несопоставимость.

Для обоих запусков:

- `temperature=0`;
- `max_tokens=2048`;
- `response_format` целиком взять из `judge_run_config.json`, включая strict JSON Schema;
- один вызов на один `request_id`, всего 16 вызовов на судью;
- новый судья не должен видеть ответы или оценки другого судьи.

Сначала можно проверить две строки, затем продолжить той же серией с теми же
параметрами. Повторять только пропуски, невалидный JSON, нарушение схемы,
неполный набор R-критериев, несогласованность `critical_errors`/`safety` и
технические ошибки. Повтор выполняется с прежними `request_id` и параметрами.
Низкие или неудобные содержательные оценки повторять нельзя. В итоговой выгрузке
должно остаться ровно по одной записи на каждый из 16 идентификаторов.

## Что вернуть

Распаковать результат в `results/adapter_strength_v1/judges/incoming/` либо
передать путь к такой папке анализатору:

```text
incoming/
├── runs.json
├── qwen_results.jsonl
├── gemma_results.jsonl
├── errors.jsonl
└── raw/
    ├── qwen_new_output.jsonl
    └── gemma_new_output.jsonl
```

Каждая строка `qwen_results.jsonl` / `gemma_results.jsonl` должна содержать:

```json
{
  "request_id": "исходный uid",
  "run_id": "фактический id запуска",
  "judge_model": "Qwen3.8-27B или gemma-4-31B-it",
  "candidate": "необязательно; если есть, точная строка judge_mapping.json",
  "score": "полный разобранный объект по judge_response_schema.json",
  "raw_response": "исходная строка JSON-ответа модели"
}
```

Это описание контейнера, а не образец оценки: в настоящей выгрузке `score`
должен быть JSON-объектом, проходящим исходную схему, со всеми обязательными
полями и фактическими баллами модели. `json.loads(raw_response)` должен быть
в точности равен объекту `score`.
Каждая строка raw-файла должна содержать как минимум `uid` и исходный
`model_response`; желательно также сохранить response id, finish reason, usage,
фактически возвращённое имя модели и техническую ошибку, если она была.

`runs.json` — массив ровно из двух фактических успешных запусков. Для каждого
нужны `id`, `model`, `status`, `count=16`, `failed_count=0`, `created_at`,
`updated_at`, `parameters`, полный `response_format`, `catalog` (`name`,
`provider`, `engine`, `backend`, `aliases`), `usage` и обязательное поле
`system_prompt_sha256` с указанным выше хешом фактически переданного промпта.
Не включать ключи, токены, cookie, внутренние YT-пути или локальные абсолютные пути.

Для GigaHF проще использовать тот же процесс импорта таблицы, что в прежнем
пилоте: `uid=request_id`, общий DAG system prompt, user prompt из соответствующей
колонки, параметры и JSON Schema из пакета. Сырые output/failed таблицы нужно
выгрузить до любой ручной правки. `errors.jsonl` должен сохранить все попытки и
причины повторов; пустой журнал означает отсутствие ошибок, а не отсутствие файла.

## Офлайн-проверка и пересчёт

Из корня репозитория:

```bash
python3 script/analyze_adapter_strength_v1_judges.py --verify-endpoints-only
python3 script/analyze_adapter_strength_v1_judges.py \
  --input-dir /path/to/incoming
```

Вторая команда не обращается к API. Она остановится при пропуске, постороннем
или повторном ID, несовпадении mapping, схемы, R-критериев, raw/parsed JSON,
`critical_errors => safety=1`, модели или протокола. После успешной проверки она
создаст 16 новых и 32 объединённые оценки на судью, `summary.json`,
`paired_cases.json`, сырые ответы, метаданные и предварительный `analysis.md`.

Автоматический отчёт не заменяет последний содержательный разбор: нужно отдельно
заполнить `adjudication_notes.json`, проверить спорные severity-решения,
расхождения судей, нумерованный цикл в dev3_29 и только затем ответить на вопросы
A–E. Review не считается прохождением; положительный результат на этой восьмёрке
является лишь основанием для расширенной проверки.
